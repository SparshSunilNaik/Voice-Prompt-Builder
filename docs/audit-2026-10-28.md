# Voice Prompt Builder: feature and security review

This is the pre-remediation snapshot. Implementation and verification continued afterwards; see [current test results](test-results.md) and [human beta acceptance](beta-checklist.md) for the current build. The findings below describe the original reviewed checkout.

Date: 28 October 2026. Reviewed checkout: `2a988dd`.

Context: [shared product/development conversation](https://chatgpt.com/share/6ae16f02-46f4-83e8-a41f-0b0aec5d821f?ogimg=plain), README, application source, manifests, build configuration, startup scripts and existing tests.

## Assessment

The concept is a useful hackathon MVP: voice capture, methodology selection, clarification and explicit approval provide more value than simple transcription. The architecture is appropriately small. Provider credentials stay in the backend; the extension has a limited site allowlist; model output is parsed and validated; transcript and final prompt editing are supported; insertion code does not click Send or dispatch Enter; and deterministic tests cover many individual components.

The current checkout is not yet reliably demo-ready. The production content script cannot load as configured, clarification context is incomplete, and workflow recovery and repeat usage have blocking defects. Public distribution needs stronger local API access controls, resource limits and privacy controls. These conclusions concern the reviewed code, not the historical claims in the conversation.

This is a bounded source/build review, not proof that all vulnerabilities have been found. No live Gnani/OpenRouter requests, physical microphone recording, or authenticated ChatGPT/Claude/Gemini browser flows were performed. No remote-code-execution or website-to-extension exploit was demonstrated. Local backend findings assume a process or extension can reach the loopback service; ordinary untrusted website origins are rejected in the tested request path.

Evidence labels: **Reproduced** means a build, parser, mocked request or isolated probe demonstrated the behavior. **Source** means a direct code path establishes the issue. **Risk** means impact or timing still needs an adversarial/live-browser test. High/medium/low are contextual priorities for this local MVP, not CVSS scores.

## Findings by feature

### Packaging and chat insertion

**1. HIGH — Production content script is emitted as an ES module but registered as a classic script. Reproduced.**

`extension/vite.config.ts` builds multiple entries with shared chunks. The generated `extension/dist/content.js` starts with `import{r as e,t}from"./assets/messages-SjGMNczF.js";`. `extension/public/manifest.json` registers that file in `content_scripts`, which does not declare module execution. Parsing the artifact with `new vm.Script(...)` fails. A successful Vite build does not validate Chrome's content-script loading contract. This blocks the insertion listener and explains the reported “page is not ready” symptom. Build the content entry separately into a self-contained classic script, then load the unpacked production extension and verify it on all three sites.

**2. MEDIUM — Insertion overwrites an existing composer draft without warning. Source.**

`extension/src/adapters/editor.ts:setEditorValue` replaces the entire textarea value or selects all contenteditable contents before inserting. Approval does not explain that an existing draft will be replaced. Offer replace/append/cancel when a draft exists, and preserve enough information to recover from an unsuccessful replacement.

**3. MEDIUM — `firstVisible` does not test visibility or editability. Source.**

In `extension/src/adapters/editor.ts`, candidates are checked only for a `disabled` attribute and their own `aria-hidden`. Hidden styles, hidden ancestors, `inert`, `readonly`, `aria-disabled`, and actual layout are not checked. Duplicate/hidden matching editors can be selected. Verify visibility and editability before any mutation.

**4. MEDIUM — Insertion verification can report success before a controlled editor rejects the change. Risk.**

`insertWithAdapter` checks DOM text for up to three animation frames and returns immediately on a match. The fallback assigns `textContent`, which may not update a rich editor's underlying state; later reconciliation can erase the text. Failures also have no rollback. Test actual ProseMirror/Quill/site editors, delayed reconciliation, multiline text and existing drafts.

**5. MEDIUM — Approval is not tied to a displayed destination, and insertion has no in-flight guard. Source/Risk.**

`extension/src/background/index.ts` queries the active tab at message-handling time. The review screen does not show a destination tab/conversation. `App.tsx:insert` has no pending flag, request identity or stale-result protection, so repeated clicks or navigation while a response is pending can produce confusing mutations or late completion transitions. Show the destination, associate approval with it and disable duplicate insertion until it settles.

### Local API security and resource handling

**6. HIGH — Local API access is not paired to this extension. Reproduced.**

`backend/app/main.py:browser_origin_guard` accepts every syntactically valid Chrome extension origin if `X-Extension-Request` equals `1`. Requests without Origin also bypass the guard. Mocked `/api/analyze` probes returned 200 for no Origin and for an unrelated 32-character extension ID with the marker; an untrusted website origin returned 403. Another extension with loopback host access or a local process can use the backend's configured provider accounts without obtaining the keys. Pair the extension with a local random secret, narrow allowed origins and keep the safe loopback launch default. CORS and a public constant header are not authentication.

**7. MEDIUM — No request concurrency, rate or provider-spending limits. Source.**

Routes construct provider clients per request. No semaphore, queue, per-client throttle, request budget or circuit breaker limits repeated analysis, generation or transcription. Combined with finding 6, this exposes quota and availability. Add bounded concurrency and request budgets; expose actionable quota feedback.

**8. HIGH — Audio conversion lacks process/output resource limits. Source; worst-case impact is a risk.**

`backend/app/services/audio.py` invokes FFmpeg and awaits `process.communicate()` without a timeout. There is no duration/output ceiling during decoding, concurrency limit, captured-stderr bound, explicit protocol restriction or cancellation cleanup that kills and reaps the child. It reads the entire decoded WAV before checking duration. Malformed or highly compressed input can monopolize CPU, disk or memory; exact resource-exhaustion payloads were not executed. Apply strict decode deadlines, output limits, supported-format checks, protocol restrictions and child-process cleanup before accepting untrusted uploads.

**9. MEDIUM — Audio type and duration enforcement is incomplete. Reproduced/Source.**

`validate_audio` trusts a filename suffix or supplied MIME type. WAV gets a duration check and WebM gets conversion plus a WAV check; MP3/OGG/FLAC/AAC/M4A return directly without decoding or duration validation. An isolated probe accepted `b'not audio'` as `fake.mp3`. Long compressed audio can bypass the advertised server duration limit. Probe and validate actual media content/duration for every accepted format before provider submission.

**10. MEDIUM — Endpoint audio limits are applied after multipart parsing. Source.**

`backend/app/api/routes.py:transcribe` reads at most the configured limit plus one byte from an already parsed `UploadFile`. That bounds this read, but does not impose an equivalent raw HTTP upload limit before the multipart parser consumes/spools the request. Add a bounded incoming-body policy, including chunked uploads, and test multipart field/file limits.

**11. MEDIUM — Nested model fields permit oversized requests and provider context. Reproduced.**

`backend/app/models/contracts.py` caps top-level input and several fields, but analysis goal/context/output/domain, many string lists, answer IDs, question IDs and individual choices have incomplete size/count bounds. A valid `IntentAnalysis` accepted a 1,000,000-character goal. Clients can submit it to refinement/generation despite the 20,000-character rough-input cap. Bound every nested field and the aggregate serialized request/provider context.

### Clarification, methodology and generated prompt quality

**12. HIGH — Generation loses the question text associated with follow-up answers. Reproduced.**

`extension/src/services/api.ts:generate`, `GenerateRequest` and `backend/app/services/prompt_engine.py:generation_user_prompt` transmit only question ID, answer and skipped state. The backend is stateless and does not retain `/refine` output. A generated ID such as `q1` with answer `Yes` cannot reliably tell the generator what was confirmed. The probe confirmed a payload containing `{'question_id': 'q1', 'answer': 'Yes'}` with no questions. Send validated question/answer pairs, or retain the question set under a workflow ID and resolve answers against it. Reject unknown answer IDs.

**13. MEDIUM — Extracted requirements and risks are not reviewable in the UI. Source.**

`extension/src/components/WorkflowViews.tsx:MethodologyReview` shows the goal and methodology options but not extracted context, constraints, known/missing requirements, ambiguities or risks. Those fields are forwarded to generation. Model-inferred requirements can therefore influence the prompt without a clear confirmation step. Show a compact editable summary of the facts that matter.

**14. MEDIUM — Intent preservation and assumption separation rely on model instructions. Risk.**

Pydantic validates structure, lengths and IDs, not whether an analysis invents requirements, whether a prompt obeys a selected approach or whether assumptions leak into its body. Pasted external text may contain adversarial instructions. There are no quality evaluations for contradictory constraints, ambiguous yes/no answers, skipped information, hallucinated facts, prompt injection or multilingual requests. Add representative evaluations and explicit provenance for user-confirmed facts. This does not establish an execution exploit: the model here has no tool-execution capability.

**15. MEDIUM — Requested revisions are only partly implemented in the UI. Source.**

The backend supports `revision_request`, but `App.tsx` always passes the fixed instruction “Create an improved alternative while preserving confirmed decisions.” There is no field to say “make it shorter” or “preserve this paragraph.” Edits may be reworked by regeneration without specific user guidance. Provide a revision field and clearly indicate which edits will be preserved.

**16. MEDIUM — Going back through methodology clears all clarification answers. Source.**

`workflowReducer:SET_QUESTIONS` recreates the complete answer map with empty answers. `App.tsx:refine` is called again even when the selected approach is unchanged. Users returning to review the approach must answer again, incurring another model call. Preserve compatible answers and invalidate them only when their associated questions change.

**17. LOW — Unanswered questions and explicitly skipped questions are treated differently without a clear decision. Source.**

The UI allows generation with every answer blank. `generation_user_prompt` omits blank unskipped answers from both confirmed answers and skipped IDs. Combined with missing question context, the generator cannot tell which missing topics were shown. Define blank answers as skips or ask the user to answer/skip, without making optional clarification mandatory.

### Workflow persistence and recovery

**18. HIGH — Reloading during work can restore a permanently inactive loading/recording screen. Source.**

`useWorkflow.ts` persists every stage and hydrates it unchanged. `App.tsx` starts requests from event handlers, not from a recovery mechanism. Reopen with `analyzing`, `transcribing` or `generating` saved and the loading screen has no request, retry or cancel behind it. `listening` can likewise restore without an active capture. Normalize transient stages to a recoverable checkpoint with an interrupted-operation notice.

**19. HIGH — Successful insertion leaves the user at a persistent dead end. Source.**

`App.tsx` renders only a completion message for `complete`; there is no New prompt, Back, Copy or reset control. That stage is persisted, so closing/reopening does not fix repeat usage. A `RESET` reducer action exists but is never dispatched by the app. Add a visible new-workflow action and recovery access to the final prompt.

**20. MEDIUM — Saved state has no runtime schema validation or version migration. Source.**

`useWorkflow.ts` casts parsed storage data to `WorkflowState`. Valid JSON such as `null`, a partial object or an older incompatible schema can break rendering or restore inconsistent state. Storage quota/write failures are silently ignored for Chrome storage; fallback localStorage access can throw. Validate, version and migrate persisted state and show a useful recovery option.

**21. MEDIUM — Sensitive workflow content is retained indefinitely with no clear-data control. Source.**

`chrome.storage.local` stores original input, transcript, answers, final prompt and analysis on state changes. These can contain secrets or personal information even though provider API keys are excluded. There is no expiry, opt-out, session-only mode or accessible reset/delete action. Use a deliberate retention policy and restrict storage access to trusted extension contexts where possible. Normal page JavaScript was not shown to read this storage.

**22. MEDIUM — Workflow state can become stale across edits and multiple side panels. Source/Risk.**

`SET_INPUT` and `SET_ANALYSIS` preserve downstream state and old methodology instructions. A new request can inherit instructions from an earlier attempt. Storage has one global key and no `onChanged` reconciliation, revision counter or per-window/workflow identity; concurrent panels can overwrite each other's saved state. Invalidate derived state deliberately and give workflows independent identities.

**23. MEDIUM — Error recovery restarts the wrong stage and frontend requests cannot be cancelled. Source.**

`App.tsx:FAIL` moves every failure into one error screen whose Try again always returns to welcome. A generation failure hides existing prompt/answer recovery instead of retrying generation. `services/api.ts` has no AbortController, deadline or response-schema validation, and App has no request IDs to ignore stale results. Add stage-aware retry, cancellation and response validation.

### Voice capture and microphone onboarding

**24. MEDIUM — Recorded audio remains referenced after stop/transcription. Source.**

`useRecorder.ts` stores audio in `chunks.current`. The array is reset only on the next `start`, not by `release`, cancellation or successful completion. The recorder/event handlers may also survive until garbage collection. This contradicts the UI's immediate-discard wording even though audio is not persisted to storage. Clear refs and handlers after constructing the upload Blob, then release upload references after completion. This is an in-memory retention issue, not confirmed disk storage or exfiltration.

**25. MEDIUM — Permission cancellation and recorder restart have asynchronous races. Risk.**

`microphonePermission.ts` installs the cancellation callback only after awaiting the initial permission query; `App.tsx:beginRecording` has no operation token to invalidate its continuation. Cancelling during that gap can be followed by recording once the permission promise resolves. Recorder `onstop` also uses shared mutable refs; cancelling then rapidly restarting could let an older stop handler affect the newer capture. Add capture/request identity checks and test delayed permission/cancel/restart event sequences.

**26. MEDIUM — Microphone permission coordination is shared across windows and lacks lifecycle recovery. Risk.**

The background tracks one permission tab globally and broadcasts its result. Multiple side panels can await the same grant and then independently begin capture. Side-panel unmount does not explicitly cancel its permission flow; a worker restart/tab-close timing can leave the UI waiting without a visible deadline. Bind requests to a panel/workflow ID, clean up listeners on unmount and test two windows plus worker suspension.

**27. LOW — Speech language and recording format controls are limited. Source.**

Gnani language defaults to `en-IN` and has no UI selector or automatic mode in this client. Recording has a 60-second cap but no front-end byte cap. If no preferred recorder format is supported, `api.ts` still names any non-OGG output `recording.webm`, potentially mislabeling the browser default. Keep language support claims scoped to what is configured and derive upload suffixes from actual supported media types.

### Provider reliability, setup and usability

**28. MEDIUM — A provider refusal/null content produces an unhandled exception. Reproduced.**

`OpenRouterClient.structured` passes `message.content` directly into `parse_json_content`, which calls `.strip()`. The surrounding handler catches TypeError and ValueError but not AttributeError. A mocked successful HTTP response with null content and a refusal raised `AttributeError: 'NoneType' object has no attribute 'strip'`, rather than an actionable ProviderError. Validate content type and refusal/finish reason before parsing. Transport protocol errors outside the narrow caught network exceptions also need structured handling.

**29. MEDIUM — Provider retries and sequential stages have no total latency/cost budget. Source.**

Analysis, refinement and synthesis are sequential calls, each permitting a second attempt. No output-token limit is passed to OpenRouter; no overall workflow deadline exists; successful usage metadata is discarded by the UI; retry usage is not aggregated; and invalid-output retries repeat the same request without diagnostic feedback. A long workflow can be expensive while the UI says it usually takes a few seconds. Add explicit completion caps, total deadlines, bounded retry policy and meaningful progress/cost feedback. Both providers instantiate fresh HTTP clients per request, foregoing shared connection pooling.

**30. MEDIUM — Setup reproducibility and release verification are incomplete. Reproduced/Source.**

The README promises Node 20+, but locked `jsdom@30.1.3` and related packages require `^22.22.2 || ^24.15.0 || >=26.0.0`; npm emitted engine warnings on Node 24.11.1. Many frontend dependencies use `latest`, startup uses `npm install` instead of `npm ci`, and Python transitive dependencies are not fully locked. Windows `start.ps1` does not explicitly check native exit codes after pip/npm/build, so `$ErrorActionPreference = 'Stop'` alone does not reliably stop native-command failures under common PowerShell configurations. The extension hardcodes port 8000 while the settings model exposes PORT; launch scripts likewise hardcode host/port and do not consume LOG_LEVEL. Health reports key presence rather than actual provider readiness, and the README's placeholder names differ from the placeholders recognized by settings. Finally, tests exercise mock providers and simple DOM fixtures rather than the packed extension in Chrome; no automated release gate detects finding 1. Pin/document a compatible runtime, make installation deterministic, check exit codes, align configuration, and add a production-extension smoke test. No login/database/billing is expected for this local MVP.

## Additional UX observations

The source has useful focus styles, reduced-motion support and editable plain-text output. It also uses many 9–11px labels, truncates button captions, enforces a 320px minimum body width while hiding horizontal overflow, provides no live-region status on loading/copy success, and does not explicitly move focus when stages change. Verify narrow panels, browser zoom, keyboard flow and screen readers. Visual quality was assessed from source and the product context; this review did not render a screenshot or perform a contrast audit.

The Copy fallback is useful on the review screen, but the claim that it is permanent does not hold for completion and error screens. There is also no measured evidence yet that refined prompts improve task success compared with the user's original prompt. A small evaluation set spanning coding, writing, research, multilingual speech and ambiguous requests would make the product claim defensible.

## Recommended fix order

1. Repair production content-script packaging; smoke-test unpacked production output in Chrome on ChatGPT, Claude and Gemini.
2. Preserve question text with answers; test ambiguous answers and skipped questions through the complete pipeline.
3. Add New prompt/reset, interrupted-workflow recovery and stage-specific retry.
4. Protect existing drafts; verify destination and controlled-editor persistence before reporting insertion success.
5. Pair the extension/backend and bound request, provider and FFmpeg resources.
6. Correct audio retention/privacy wording and add data deletion/retention controls.
7. Handle provider refusals and malformed responses; improve revisions and fact review.
8. Pin supported runtimes and introduce a repeatable real-Chrome release check.

No application source was changed by this review. The report is the only new non-ignored project file; installed dependencies, built output and the isolated probe remain in ignored local directories.
